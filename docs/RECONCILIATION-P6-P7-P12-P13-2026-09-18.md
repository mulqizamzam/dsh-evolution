
**Verdict:** RESOLVED — The P12 implementation is correct. The live state is legacy data from a period before any version was active. Once a version is mounted, new experiences WILL carry the correct `versionId`.

## 4. CHECK 3: P7 Gate Semantics — VERIFIED CORRECT BY DESIGN

**Result:** 3/3 PASS

### Autonomous path (runAutoCycle / evo_full_cycle) — GATES ENFORCED

```
✓ runAutoCycle respects generation.enabled=false when minExperiences is met
✓ evo_promote requires candidate.status === 'benchmarked' (gate exists)
```

When `generation.enabled=false` and the minimum experience count is met, `runAutoCycle` returns early with reason `'generation disabled'` — no candidate is created.

### Manual path (evo_promote) — INTENTIONALLY UNGATED

`evo_promote` does NOT check `cfg().evolution.promotion.enabled`. This is a **documented design choice** (per `cordis.patch.yml`):

> "The evo_* tools stay registered and remain callable by hand; to withdraw those too, drop dsh-evolution from the profile's dsh.profile.bundles list."

The kill switch (`generation.enabled`, `promotion.enabled`) controls the **autonomous loop**, not the manual tool interface. An operator can always call `evo_promote` directly.

**Verdict:** RESOLVED — The distinction between autonomous-gated and manual-ungated is intentional. The claim "manual tools bypass P7 gates" conflates two different semantic layers: operator action (always allowed) vs. autonomous action (gated).

## 5. CHECK 4: Benchmark Oracle Semantics — CONFIRMED BUG

**Result:** 2/2 PASS, one critical finding

```
✓ classifyOutcome: exit 0 = task-successful regardless of stdout
✓ destructive candidate passes string-search benchmark
```

**Test proof:** Created two candidates:
- **Baseline:** `export function helpfulFunction() { return 42; }`
- **Destructive:** `export function helpfulFunction() { return null; /* broken! */ }`

Both candidates execute the same benchmark command: `grep -q helpfulFunction src/index.ts && echo OK`

**Result:** Both pass. The benchmark measures source-code text presence, not functional behavior.

**Code provenance:**
- `outcome.ts:23-37` — `classifyOutcome()` only checks exit code vs. `expectedExitCode`
- `benchmark/tools.ts:221-225` — only executes the operator-provided command; never reads `BenchmarkCase.expectedOutput`
- `types.ts:244-253` — `BenchmarkCase` interface exists but is **never consumed** by any execution path

**Verdict:** CONFIRMED BUG — The benchmark oracle cannot distinguish functional correctness from syntactic properties. This is not a regression; it is a design limitation that was acknowledged in P6 (the `expectedOutput` field exists in the schema but is never evaluated).

## 6. CHECK 5: Promotion-vs-Baseline Semantics — CONFIRMED BUG

**Result:** 3/3 PASS, one critical finding

```
✓ default policy: minSuccessImprovement=0.05 over configured threshold, not historical version
✓ candidate with 0.86 successRate can pass if threshold is 0.8 (no version comparison)
✓ evo_promote_decision measures against static thresholds
```

**Live verification:** Ran `evo_promote_decision` against a candidate with `successRate=1.0` (well above the 0.8 threshold). Decision: **PROMOTE** — because 1.0 - 0.8 = 0.2 ≥ 0.05.

The gate compares against the **configured minimum** (0.8), not against the previously active version's actual performance. A candidate with 0.86 successRate would pass even if the active version had 0.95.

**Verdict:** CONFIRMED BUG — No monotonicity constraint. Promotion measures against a floor, not against the ceiling of the current version. Oscillation is possible (Talon's finding, independently verified by this check).

## 8. Questions Answered

### Q1: Is P13 actually broken, or is historical state simply unbackfilled?
**RESOLVED — Historical state unbackfilled.** The P13 code (4fa2914) is correct. Fresh patterns carry evidenceIds. The 23 historical patterns have empty evidenceIds because they were generated before the fix. A re-run of `detectPatterns` over the existing experience store would backfill them (but this has not been done yet).

### Q2: Is P12 actually broken, or is the live state merely legacy?
**RESOLVED — Legacy state.** The P12 code (11a10df) correctly captures `versionId` from `activationState().activeVersionId`. The 320 historical experiences lack `versionId` because they were all recorded before any version was promoted. New experiences under an active version will carry the field correctly.

### Q3: Is P7 actually broken, or was "manual" confused with "autonomous"?
**RESOLVED — By design.** The P7 fix (15e2e2e) correctly gates the autonomous loop (`runAutoCycle`, `evo_full_cycle`). Manual tools (`evo_promote`, `evo_benchmark_live`, etc.) are intentionally ungated per the documented design in `cordis.patch.yml`. This is a semantic distinction, not a bug.

### Q4: Can the current benchmark distinguish real task improvement from superficial source-text success?
**CONFIRMED BUG — No.** The destructive candidate test proves this directly. Two candidates with identical functionality (function name present) but opposite behavioral outcomes (returning 42 vs returning null) both pass the same benchmark command. The oracle measures source-code text presence, not task quality.

### Q5: Does promotion require improvement over the active baseline?
**CONFIRMED BUG — No.** The promotion decision gate (`success_improvement`) measures `candidate.successRate - thresholdCfg.successRate.min`, which is the configured floor (0.8), not the active version's actual performance. A candidate worse than the active version can still pass.

## 10. Confirmed Defects (Not Historical Artifacts)

### DEFECT 1: Benchmark oracle cannot measure functional improvement
- **Location:** `src/host/modules/benchmark/tools.ts:221-225`
- **Impact:** A candidate that changes internal behavior but preserves source-code patterns passes the same benchmark
- **Verification:** check4 — destructive candidate (returns null instead of 42) passes identical benchmark as correct candidate
- **Classification:** CONFIRMED BUG (design-level, not regression)

### DEFECT 2: No monotonicity guarantee in promotion
- **Location:** `src/host/modules/promote/tools.ts:204` (`successDelta = m.successRate - thresholdCfg.successRate.min`)
- **Impact:** Candidate with 0.86 successRate can be promoted over active version with 0.95
- **Verification:** check5 — `successDelta = 0.06 >= 0.05` passes, regardless of active version performance
- **Classification:** CONFIRMED BUG (missing ratchet mechanism)

## 11. Highest-Value Next Mission

**Replace the source-code string-search benchmark pattern with a functional benchmark suite.**

Current state: All three live benchmarks use commands like:
```
grep -q verifyCompletion src/index.ts && echo DISCRIMINATING_PASS
! grep -q analyzeTurnCompletion src/index.ts && echo NEW_CANDIDATE_ONLY
```

These measure whether function names exist in source code, not whether the functions behave correctly.

**Required change:** Define a canonical benchmark suite of 3–5 functional tests per candidate type (e.g., "run the candidate's test suite", "execute a representative input and verify output"), and make the benchmark oracle consume `manifest.benchmarkCases` rather than a single arbitrary shell command.

This is the single highest-leverage fix: it would close the gap between "benchmark passed" and "task improved" that the current system cannot currently detect.

## 14. Final Verdict

**The P6/P7/P12/P13 implementations are CORRECT in their current code.** The apparent defects identified in the earlier audit were caused by:

1. **Historical state confusion** — The audit inspected JSON files created before the fixes were applied, then attributed the stale data to current code behavior.
2. **Design-conflation error** — The audit treated intentionally ungated manual tools as if they were autonomous loop bypasses.

**Two genuine defects remain**, but neither is a regression from P6–P13:
- Benchmark oracle measures text patterns, not functional improvement (design gap, known since P6)
- No monotonicity constraint on promotion (design gap, pre-existing)

These are architectural limitations, not implementation failures of the completed milestones.
