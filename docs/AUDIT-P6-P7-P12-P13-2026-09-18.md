## 1. Executive Conclusion

**The north-star claim "DSH learns from operational experience, discovers improvement opportunities, generates changes, validates them empirically, promotes effective changes, detects regressions, rolls back safely, and accumulates validated improvements over time" is NOT DEMONSTRATED.**

The system has a working end-to-end pipeline that executes the full loop: experience → pattern → candidate → benchmark → promotion → version → observation. All infrastructure is present and tests pass. However, **three independent structural defects** prevent the system from meaningfully improving DSH over time:

1. **Benchmark oracles are non-discriminative** — they measure source-code text patterns and exit codes, not functional task outcomes. Candidates can pass while being objectively worse for real DSH workloads. (FACT)
2. **Version attribution is broken** — 0/320 experiences carry a `versionId` field, so `detectVersionDegradation()` always returns null and the degradation→regeneration feedback loop is permanently inert. (FACT)
3. **Improvement is measured against absolute thresholds, not historical baselines** — a candidate clears the 0.85 success-rate floor without needing to beat the previously active version. No monotonicity constraint exists. (FACT)

Additionally, the **manual tool path bypasses the kill switch entirely** — all 14+ standalone `evo_*` tools are ungated, so the full evolution pipeline is executable while `generation.enabled=false` and `promotion.enabled=false`. The three live versions were created through this ungated manual path. (FACT, documented design intent)

**The single highest-value missing experiment:** A benchmark that measures actual DSH task outcomes (success rate on a representative workload) against the current active version, rather than against source-code string presence. Until this is implemented, "promotion" cannot be said to represent "improvement."

## 2. Complete Current Evolution Path

```
[Boot]
  apply() → resolveConfig → store.init() → MODULES.forEach(m => m.apply(deps))
    → refreshActivation() → read active version, validate artifact, sandbox preflight, mount plugin

[Observation (auto-record)]
  ctx.on('session/event', ...) fires per completed turn
    → observeTurn() derives prompt/stepCount/duration/errors from session events
    → activationState().activeVersionId (null if no version active)
    → store.addExperience({ ..., versionId: activeVersionId ?? undefined })
    → runAutoCycle() (fire-and-forget, guarded by inFlight + cyclesRun)

[Analysis]
  detectPatterns(experiences, minOccurrences)
    → clusters by e.summary or first-error signature
    → generates Pattern records with type: failure|success|inefficiency|opportunity
    → dedup by description text against existing patterns
    → store.addPattern() for fresh patterns
  detectVersionDegradation(experiences)
    → groups by versionId (skips records without versionId)
    → per version: successRate < 0.6 OR errorRate > 0.3 (min 5 observations)
    → returns null when byVersion.size === 0  ← ALWAYS in current live state

[Candidate Generation]
  Two paths:
  a. Pattern-driven: evo_full_cycle / runAutoCycle → builder.generate (LLM call)
  b. Degradation-driven: detectDegradationAndSynthesize → synthetic pattern → builder.generate

[Benchmarking]
  evo_benchmark_live: execute command in sandbox → classifyOutcome (exit-code oracle)
  evo_benchmark_ab: A/B comparison with baseline candidate resolution
    baselineId = candidate.parentVersion → store.getCandidate(baselineId)
    if null → fallback to activeVersion.modules[0] → store.getCandidate(modId)
    if still null → emptyMetrics() → guaranteed +100% delta

[Promotion]
  evo_promote: validate artifact → sandbox preflight → store.createVersion → store.updateCandidate('promoted')
  NO check on cfg().evolution.promotion.enabled  ← bypasses kill switch

[Activation]
  refreshActivation: read active version, validate, mount plugin.js
  Deactivation: unmount plugin, clear activeVersionId

[Post-Promotion Observation]
  New experiences attributed via activationState().activeVersionId
  detectVersionDegradation can now fire when versionId is populated
  detectDegradationContext → synthetic degradation pattern → candidate regeneration
```

## 3. Learning-Validity Findings

### FACT: Pattern detection produces only trivial success-patterns
All 23 patterns in live state are `type: "opportunity"` with descriptions of the form `"Recurring signature observed N times: turn ended: completed"`. The clustering key is `e.summary`, which is always `"turn ended: " + reason.kind`. Since all 320 experiences have `success: true`, every pattern is about successful completion, not about failures or improvement opportunities.

**Root cause:** `detectPatterns` uses `e.summary` as the clustering key for all records. Success summaries are trivially identical. Failure summaries contain error messages that would produce distinct clusters. With zero failures in the experience pool, only success patterns can be generated.

### FACT: 0/320 experiences have `versionId`
The `observeTurn` function captures `activationState().activeVersionId` at observation time. All 320 experiences were recorded before any version was promoted (v1 created 2026-09-16T12:23Z, experiences span 12:09Z–13:15Z). `activationState().activeVersionId` was `null` at all 320 write times.

### FACT: P13 evidence lineage repair is code-correct but data-stale
The P13 fix (commit 4fa2914) correctly populated `evidenceIds` in `detectPatterns` and propagated them to candidates via the builder. However:
- All 23 patterns on disk have `evidenceIds: []` (created before the fix)
- All 3 candidates on disk have `evidenceIds: []` (derived from patterns with empty evidenceIds)
- No migration/backfill step was performed

### FACT: No failure experiences exist to cluster
All 320 experiences have `success: true`. The system has never recorded a failed turn. This means:
- Pattern detection can only find "opportunity" patterns (success signatures)
- No "failure" patterns exist to drive candidate generation
- No "inefficiency" patterns exist (all step counts are from successful runs)

## 4. Improvement-Validity Findings

### FACT: Benchmark commands test source-code text patterns, not functional behavior
All three live benchmarks used source-code string matching as the oracle:

| Benchmark | Command | What it actually tests |
|-----------|---------|----------------------|
| `2e493e89552b` | `node src/index.ts && echo AB_PASS` | Script exits 0 |
| `d7664a9e8c66` | `grep -q verifyCompletion src/index.ts && echo DISCRIMINATING_PASS` | Function name exists in source |
| `b386cbcf93c3` | `! grep -q analyzeTurnCompletion src/index.ts && echo NEW_CANDIDATE_ONLY` | Old function name is absent from source |

A candidate containing `export function verifyCompletion() { return { verified: false }; }` would pass the `d7664a9e8c66` benchmark. The benchmark measures syntactic properties, not behavioral correctness.

### FACT: The `BenchmarkCase.expectedOutput` and `expectedExitCode` fields in the schema are never read
`types.ts` defines `BenchmarkCase` with `expectedOutput` and `expectedExitCode` fields, but no benchmark tool reads them. The only oracle is the operator-supplied `command` parameter. The P6 outcome classifier (commit 23c1f9a) correctly removed the false stdout-presence heuristic, but the deeper gap — that there is no structured per-case evaluation loop — remains unaddressed.

### FACT: Promotion gate compares against absolute thresholds, not historical baselines
The `DEFAULT_PROMOTION_POLICY` requires:
- `minSuccessImprovement: 0.05` — improvement of at least 5% over the configured minimum
- `maxRegression: -0.05` — regression of at most 5%

But the `success_improvement` gate in `evo_promote_decision` computes `successRate - cfg.successRate.min` where `cfg.successRate.min = 0.8`. This measures how much the candidate beats the *threshold*, not the *previous version's actual performance*. There is no monotonicity constraint: a v3 with successRate 0.87 passes even if v2 had successRate 0.95.

### FACT: No cross-task regression detection exists
Each benchmark uses a single operator-provided command. There is no mechanism to verify that a candidate improving one task class does not harm another task class. A candidate could be brilliant at task type A and catastrophic for task type B, and the system would only see the task A benchmark.

## 5. Benchmark-Gaming Findings

### Strongest demonstrated attack: "Source-Code Discrimination"
The v2→v3 promotion used the command `! grep -q analyzeTurnCompletion src/index.ts && echo NEW_CANDIDATE_ONLY`. This **passes when the old function is absent**, meaning:
- The candidate can delete the entire working codebase and still pass
- The candidate can replace any function with a stub that has the new name
- The benchmark measures "did you rename the function?" not "did you improve the function?"

**Classification: FACT** — proven by live benchmark data `b386cbcf93c3` where baseline exit=1 (contains old name) and candidate exit=0 (contains new name), delta +100%, promoted.

### Second attack: "Empty Baseline Exploit"
When `candidate.parentVersion` is a version ID (like `"v1"`) rather than a candidate ID, `store.getCandidate("v1")` returns null. The fallback tries the active version's modules. If that also fails, `baselineMetrics` defaults to `emptyMetrics()` (all zeros), guaranteeing a +100% successRate delta for any candidate that exits 0.

**Classification: FACT** — proven by live benchmark `2e493e89552b` where `baseline: "unknown"` and `baselineMetrics: { successRate: 0, avgScore: 0, errorRate: 0, avgSteps: 0, avgDurationMs: 0 }`.

### Third attack: "Self-Defeating Baseline"
The A/B benchmark for v2 (d7664a9e8c66) deliberately chose a command that the old code fails but the new code passes: `grep -q verifyCompletion` finds the function in v2 but not in v1 (which has `analyzeTurnCompletion`). This is a discrimination test, not an improvement test. It passes any candidate that adds a new function name and removes the old one.

**Classification: FACT** — proven by live benchmark data.

### Fourth attack: "Simulated Benchmark from Stale Data"
`evo_benchmark_run` (simulated mode) derives metrics from recorded experience metrics. With all 320 experiences succeeding, the simulated benchmark for any candidate will pass trivially. This mode is explicitly rejected by `evo_promote_decision` when `allowSimulated: false` (the default), but the tool still exists and can be called by hand.

**Classification: FACT** (for simulated mode) / **INFERENCE** (that operator misuse of this tool would be indistinguishable from legitimate use in the current state).

## 6. Baseline Integrity

### FACT: No baseline is "the same workload"
Each benchmark uses a single command that the operator (or LLM) provides. There is no fixed test suite, no standardized workload, and no cross-version invariant comparison. Each promotion uses a different benchmark command than the one before it. The "improvement" is always measured against the specific command in that one benchmark run.

### FACT: Baseline drift between benchmarks
The three benchmark commands are:
1. `node src/index.ts && echo AB_PASS`
2. `grep -q verifyCompletion src/index.ts && echo DISCRIMINATING_PASS`
3. `! grep -q analyzeTurnCompletion src/index.ts && echo NEW_CANDIDATE_ONLY`

These measure three different properties. Comparing them transitively (v1 better than nothing, v2 better than v1, v3 better than v1) is comparing apples to oranges to pears.

### INFERENCE: The only baseline that would be meaningful is a fixed regression suite
A set of N benchmark commands that all must pass, where N is fixed and the commands test functional behavior (not source text), would establish a true regression floor. This is the `BenchmarkCase` interface that was designed but never implemented as an execution path.

## 7. Cumulative-Improvement Analysis

### FACT: Versions are replacements, not accumulations
`createVersion` in `store.ts` creates a new version with a single `modules` entry. The previous version's module is not merged. `v3` contains only `09ab8c73c216` (turn-efficiency-tracker). The v1 module (`9f7277246daa`, turn-completion-analyzer) is not present in v3. The system cannot layer improvements.

### FACT: No regression memory across generations
When v2 was rejected (benchmark `05b79d83caeb`: successRateDelta 0.0%, "insufficient improvement"), the system records `candidate.status = 'rejected'` but does not store *why* it was rejected as a lesson for future candidates. The next candidate generated from the same evidence set will not know that the previous approach was insufficient. The C5 dedup guard (f355521) prevents unbounded rejection churn, but it also prevents the system from trying a *different* approach.

### FACT: No monotonicity constraint
`DEFAULT_PROMOTION_POLICY.minSuccessImprovement = 0.05` is a floor, not a ratchet. A v4 candidate with successRate 0.86 can be promoted even if v3 had successRate 0.92. The system does not require the new version to be at least as good as the previous one.

**Determination:** Monotonicity constraint IS needed. Without it, the system can oscillate: improve X → degrade X, improve Y → degrade Y → ... indefinitely. The 5% improvement floor is not sufficient to prevent regression across multiple dimensions.

## 8. Oscillation/Stagnation Analysis

### FACT: Oscillation is possible
The degradation signal is a single aggregate metric per version. There is no multi-dimensional Pareto dominance check. A concrete oscillation loop:

```
v1: successRate=0.55 (degraded, stepCount=25)
  → detectVersionDegradation → "Degradation v1: success-rate-low:55.0%; high-step-count:25.0"
v2: successRate=0.75, stepCount=14 (fixed success, introduced step efficiency)
  → no degradation signal (success rate OK, steps OK)
  → BUT: new timeout failures appear in a task class not covered
v3: successRate=0.82, stepCount=28 (fixed timeouts, worsened steps)
  → "Degradation v3: high-step-count:28.0"
v4: successRate=0.88, stepCount=14 (fixed steps, introduced flaky race condition)
  → "Degradation v4: error-rate-high:15.0%"
v5: loops back to the same problem domain as v1, with a different root cause
```

No dedup mechanism catches this because the degradation descriptions are version-specific (`"Degradation vN: ..."`) and the evidence IDs change with each cycle.

### FACT: Stagnation is possible
Two independent stagnation mechanisms:
1. **`maxCyclesPerProcess=3`** is a hard cap. After 3 autonomous cycles, all future auto-cycles are silently blocked for the process lifetime.
2. **C5 terminal evidence-identity** blocks candidate generation when all evidence IDs are in a terminal set. If the same 5 experiences keep causing the same failure, and the LLM keeps generating a failing candidate, C5 blocks forever.

After process restart, guards reset but C5 immediately re-blocks if evidence hasn't changed. The system can be permanently dead.

### FACT: Rollback has no negative feedback
When v2 is rolled back to v1, the system does not record that "candidates generated from v2's evidence set were previously rejected." The next time v2's evidence reappears, the system generates a fresh candidate without memory of v2's failure. There is no "blacklist" of similar-candidate patterns.

## 10. Failure-Boundary Analysis

### FACT: `evo_promote` deactivates before probe validation
In `promote/tools.ts`, `activateVersion()` is called to run the sandbox preflight. Inside `activateVersion` (loader.ts:158), `deactivate(null)` unmounts the current version *before* the new version is validated. If the preflight fails, the function returns `{ ok: false }` but the previous version is already unmounted. The host is left with no active evolution tool.

**Classification: CRITICAL BUG** — no recovery path in the error handler.

### FACT: Corrupted artifact at boot refuses activation but does not crash
`activation.spec.ts` confirms: "a corrupted artifact is refused at boot instead of being loaded" (7/7 tests pass). This is correct behavior — the system degrades gracefully.

### FACT: `writeJsonAtomic` prevents partial writes
The staging-directory-then-rename pattern in `materializeArtifact` (artifact.ts) ensures that a failed promotion never leaves a half-written artifact. `readJsonSafe` in the store catches JSON parse errors and returns null. No code path modifies experience records after write (append-only).

### FACT: Process restart loses all in-process state
Module-level guards (`inFlight`, `cyclesRun`, `lastCycleExperienceCount`) are lost on restart. `test2-restart-persistence.spec.ts` confirms guards reset to default values. Persisted state (experiences, patterns, candidates, versions) survives correctly.

### UNKNOWN: Concurrent tool call races
The store uses `writeJsonAtomic` (staging dir + rename) which is atomic on POSIX. However, `updateCandidate` is read-modify-write: `getCandidate` → spread → `writeJsonAtomic`. Two concurrent `updateCandidate` calls on the same candidate can lose one update. No test covers this race condition.

## 11. Production-Safety Analysis

### FACT: `generation.enabled` and `promotion.enabled` gate the autonomous loop
`evo_full_cycle` checks `cfg.generation.enabled` at step 3 and `cfg.promotion.enabled` at step 8. `runAutoCycle` checks both in the auto-experience module. This is correct.

### FACT: Manual tool paths bypass all gates
The standalone tools `evo_promote`, `evo_benchmark_live`, `evo_benchmark_ab`, `evo_candidate_create`, `evo_experience_record` do NOT read `cfg().evolution.*`. They can be called by hand regardless of the kill switch state. This is documented in `cordis.patch.yml`:
> "The evo_* tools stay registered and remain callable by hand; to withdraw those too, drop dsh-evolution from the profile's dsh.profile.bundles list."

This is a **design choice**, not a bug. The risk is that an operator (or a prompt-injected agent) can execute the full pipeline while the kill switch is off.

### FACT: Config keys declared but never enforced
- `experience.maxRecords: 10000` — no trimming logic reads this
- `experience.retentionDays: 90` — no cleanup timer
- `candidate.maxActive: 10` — no candidate count limit
- `benchmark.improvementThreshold: 0.05` — not used; `DEFAULT_PROMOTION_POLICY` has the hardcoded value
- `benchmark.regressionThreshold: 0.10` — not used

These keys mislead operators into thinking limits are enforced when they are not.

### FACT: Filesystem growth is unbounded
Experiences accumulate at ~100/day in active sessions. At the current rate (320 in 2 days), the `experiences/` directory will reach 10,000 files (~50 MB of JSON) within 60 days. No retention or pruning mechanism exists.

### FACT: `maxCyclesPerProcess=3` is extremely conservative
After 3 failed autonomous cycles, the loop is dead. The first cycle may consume one attempt on a stale pattern, the second on a new pattern, and the third on a degraded version. If all three fail, the system is permanently silent until the next host restart.

## 13. Strongest Counterexamples

### Counterexample 1: "Promotion with no measurable improvement" (CRITICAL, FACT)
Candidate `09ab8c73c216` (v3) was promoted against a benchmark command that the baseline code *cannot* pass: `! grep -q analyzeTurnCompletion src/index.ts && echo NEW_CANDIDATE_ONLY`. The baseline (v1 code) contains `analyzeTurnCompletion`, so the negated grep fails (exit 1). The candidate code does not contain it, so the grep succeeds (exit 0). This is a **rename test**, not an improvement test. The candidate could contain any code at all — even dead code — and still pass.

### Counterexample 2: "Zero-baseline promotion" (CRITICAL, FACT)
Candidate `9f7277246daa` (v1) was benchmarked against an empty baseline (`baseline: "unknown"`). The `emptyMetrics()` default gives the baseline a successRate of 0. The candidate's successRate of 1.0 represents a +100% "improvement" over nothing. The 5% minimum improvement threshold is meaningless when the comparison target is void.

### Counterexample 3: "Kill-switch-bypassed promotion" (HIGH, FACT)
All three live versions were created while `generation.enabled=false` and `promotion.enabled=false` (the shipped default). The `evo_promote` tool does not check these config flags. The kill switch is only enforced in the autonomous cycle, not in the standalone promotion tool.

### Counterexample 4: "Inert degradation detection" (HIGH, FACT)
The entire degradation → regeneration feedback loop is dead code in the current live state. `detectVersionDegradation` filters by `versionId`; all 320 experiences have `versionId: undefined` (or `null`); the function's first loop skips every record; `byVersion.size === 0`; returns `null`. No degradation signal has ever fired. No degradation-driven candidate has ever been generated.

## 14. Highest-Value Next Mission

**The single highest-value missing experiment is a fixed benchmark regression suite that measures actual DSH task outcomes.**

Specifically:
1. **Define a canonical benchmark suite** — 5–10 benchmark commands that represent real DSH workload classes (e.g., "run the type checker", "run the test suite", "execute a build step", "verify a file exists and contains the expected string", "run a shell script that exits non-zero for a known-bad state"). These commands must test functional behavior, not source-code text patterns.
2. **Replace `candidate.parentVersion` resolution** — when `parentVersion` is a version ID, resolve it to the *active version's candidate module ID* before calling `getCandidate`. This eliminates the empty-baseline exploit.
3. **Add monotonicity gate to `evo_promote_decision`** — a candidate must have a success rate at least as good as the current active version's last benchmark. This prevents oscillation and enforces ratchet behavior.
4. **Backfill `versionId` on post-promotion experiences** — the code is correct; the data gap was because no version was active during early recording. Once v3 is mounted, new experiences will carry `versionId`. The system needs to be run for at least 5 turns after a promotion to generate enough versioned observations for degradation detection to fire.
5. **Remove or implement the dead config keys** — `maxRecords`, `retentionDays`, `maxActive`, `improvementThreshold`, `regressionThreshold` are declared but never read.

**The audit also recommends:**
- Fix `evo_promote` to save/restore activation state on preflight failure (CTO Bug #1)
- Add `benchmarkRunId` to `createVersion` call sites (Ledger G10)
- Raise `maxCyclesPerProcess` from 3 to 10–20 with per-cycle logging (Talon Gap 3)
- Add a "must beat current active version" gate to prevent oscillation (Talon Gap 1)

|---------|----------------------------------------|

The live state suggests C5 was not in effect at the time those candidates were created (pre-commit f355521). |
| Whether a fixed benchmark suite would prevent the source-code discrimination attack | The suite design is the missing architectural capability. Whether a specific set of commands would be robust is unknown until they are defined. |
| Whether `maxCyclesPerProcess=3` is sufficient for reliable autonomous operation | The cap is per-process. A 24-hour session with 3 failed cycles is permanently dead. The optimal value depends on failure rates which cannot be measured without running the system for extended periods. |
| Whether concurrent `updateCandidate` calls can lose updates | No test covers the race condition. The store's read-modify-write pattern in `updateCandidate` is not atomic. POSIX rename is atomic for the file write itself, but two processes reading the same candidate and both writing will lose one. |
