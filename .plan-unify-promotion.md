# Plan: Unify Comparative Promotion Authority

## Problem Statement

`runPromotionPolicy` (the shared version-creation function in `src/host/modules/promote/index.ts`) captures `activeMetrics` for provenance but does NOT enforce the `beats_active` comparative gate. Both `evo_promote` (manual) and `evo_full_cycle` (autonomous) call `runPromotionPolicy`, but neither enforces the gate itself — the gate lives only in `evo_promote_decision` (an advisory tool that `evo_full_cycle` never calls).

This means `evo_full_cycle` CAN promote a candidate with success rate 0.86 even when the active version has 0.95, because:
1. `evo_full_cycle` checks `benchmarkPassed` (threshold floor 0.80) → 0.86 passes
2. `evo_full_cycle` calls `runPromotionPolicy` which does NOT compare against active → version gets created

The fix: move the `beats_active` gate into `runPromotionPolicy` so that ALL promotion paths enforce it before the version is created.

## Design

### What changes in `runPromotionPolicy`

Add a comparative check AFTER capturing `activeMetrics` but BEFORE `store.createVersion()`:

```
1. Load active version + its metrics (already done for capture)
2. If active metrics exist AND candidate has a live benchmark:
   a. Find candidate's latest live benchmark
   b. If candidate.successRate <= active.successRate → reject
3. Proceed with version creation only if gate passes
```

The check mirrors the exact logic in `evo_promote_decision` (line 273–281 of `promote/tools.ts`):
- If active version has no comparable metrics (first version, or no live benchmark on active module) → gate is skipped
- If candidate's success rate is NOT strictly greater than active → reject

### What changes in `evo_full_cycle`

- Remove the assumption comment ("beats_active gate ... behave identically")
- Add explicit handling: if `runPromotionPolicy` rejects with `beats_active`, mark candidate as rejected and return REJECTED verdict
- The existing flow already handles `!promoResult.ok` → reject, so only the rejection reason needs to be surfaced

### What changes in `evo_promote`

- No functional change needed: the preflight (artifact validation + sandbox probe) already runs BEFORE `runPromotionPolicy`, so a worse candidate will fail at the gate and the version will not be created
- The manual preflight (artifact materialize + validate + sandbox activate) is a pre-condition distinct from the full-cycle preflight (LLM build + validation + sandbox benchmark)

### What does NOT change

- P6 benchmark/oracle semantics: `latest.passed`, `latest.mode`, `latest.runs` are still the decision inputs in `evo_promote_decision`
- P7 gate semantics: `cfg.generation.enabled` / `cfg.promotion.enabled` still gate entry to autonomous paths
- `store.createVersion()`: stays as a low-level primitive; all production callers go through `runPromotionPolicy`
- `evo_promote_decision`: still runs the full policy check (benchmark_passed, min_runs, success_improvement, max_regression, latency_multiplier, beats_active) — it remains the decision tool. The change makes `runPromotionPolicy` the ENFORCING boundary that can reject independently
